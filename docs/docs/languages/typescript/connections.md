# Connections

Every protocol runs on a
[connection](../../guides/idl/protocol.md#calls-in-both-directions) unless it
picks the lockstep `datagram` framing, in which case it gets a
[client and server](client-and-server.md) instead. This page is the default
case in [What you use](index.md#what-you-use), and uses this schema:

```ids
protocol Chat {
    function send(n: u32) -> u32;
}

@provider = Client
protocol Events {
    function shown(n: u32) -> bool;
    function ping();
}
```

## Serving every protocol

The package gets one `serve`, taking a `Services` object with a field per
protocol the server provides. Leaving one out doesn't type-check.

### When they're generated

`Services`, `ClientServices`, `accept`, `serve` and `connect` are generated
when the package has one connection to serve, and left out otherwise. They're
left out when:

- **No protocol is on a connection.** That includes a package with no
  protocols at all. A protocol is on a connection when it uses `datagram@3`
  (the default) or `datagram@2`, or when the client provides it (`@provider = Client` or
  `Multiple`). A server-only protocol on `datagram@1` isn't, so a package of
  only those has no `serve`. The same goes for JSON-RPC protocols, which count
  only once one JSON-RPC protocol in the package is client-provided; then they
  all do.
- **The protocols on connections disagree** on the framing or the handshake.
  No one connection carries them all, and `comline generation` warns, naming
  both protocols. Each protocol still gets its own dispatcher and sender.
- **Only protocols from an external `std` are on a connection.** Only what
  the package emits counts.

When a package declares protocols but none is on a connection,
`comline generation` says so, and why.

### Using them

They're in `connection.ts`. In `lib` mode the package's `index.ts`
re-exports it, so import from the package; in `code` mode import from the
file, wherever you placed it. `Format` and `CONNECTION_IR_HASH` are in
`wire.ts`, which `connection.ts` re-exports.

```ts
// `lib` mode
import { connect, serve, chat } from "my-package";

// `code` mode
// import { connect, serve } from "./generated/connection";
// import * as chat from "./generated/chat";

// The side that accepts: handshake, provide every protocol, serve until
// the peer leaves.
await serve(transport, { chat: chatImpl });

// The side that dials: handshake, provide the client's protocols, and call
// the server's through their senders.
const conn = await connect(transport, { events: eventsImpl });
const sent = await new chat.ChatSender(conn).send({ n: 3 });
```

- **`accept(transport, services)`** returns the connection, already serving,
  so the server can call the client through it.
- **`ClientServices`** holds the protocols the dialling side provides
  (`@provider = Client` or `Multiple`). With none, there is no `ClientServices`
  and `connect` takes only the transport.
- **Field names** are the protocol's name in camelCase
  (`CharacterInventory` is `characterInventory`), prefixed with the namespace
  where two schemas declare a protocol of the same name.
- **The format** is the package's `Format`
  ([Framing & wire format](framing-and-wire-format.md)); the framing and
  handshake are the protocols'. When the protocols on connections disagree on
  either, no one connection carries them all, so these functions aren't
  generated and `comline generation` warns why.
- **A schema named `wire`** can't be used, since the package's `wire.ts` would
  overwrite it.

## What codegen emits

The entry points are in `connection.ts`, which opens with a comment saying, for
this package's protocols, what to implement, serve, dial and call:

```ts
// Generated by Comline
// For TypeScript 5.0 or later; verified up to 5.9.

/**
 * Where to start:
 *
 * - Implement what you provide: `Chat`, `Events` (in `./conformance.js`).
 * - Serve with `serve(transport, { chat })`; `accept(transport, { chat })` takes the same and hands back the connection.
 * - Dial with `connect(transport, { events })`.
 * - Call the other end with `new ChatSender(conn).send(…)`, on the connection `connect` returns or the peer a handler is given.
 *
 * What is marked internal is wire plumbing: exported for hand-written use, and not what
 * a user calls.
 */

import { CONNECTION_IR_HASH, Format } from "./wire.js";

/** The package's wire format and the digest of every schema in it, which every file of the package shares. */
export { CONNECTION_IR_HASH, Format } from "./wire.js";

/** What the accepting side provides: one field per protocol, so leaving one out doesn't type-check. */
export interface Services {
    chat: ns_conformance.Chat;
}

/** What the dialling side provides: one field per protocol, so leaving one out doesn't type-check. */
export interface ClientServices {
    events: ns_conformance.Events;
}

/**
 * Provide every protocol in `services` on `conn`: the peer's calls to them come here.
 * @internal
 */
export function provideServices(conn: Connection, services: Services): void { /* … */ }

// provideClientServices, the same for `ClientServices`, also `@internal`.

export async function accept(transport: Transport, services: Services): Promise<Connection> {
    const agreed = handshake();
    const conn = await Connection.accept(transport, Format, CONNECTION_IR_HASH, new Datagram3Framing(), agreed);
    conn.extensions.set(agreed.negotiated!);
    provideServices(conn, services);
    return conn;
}

/** {@link accept}, then serve every call until the peer leaves. */
export async function serve(transport: Transport, services: Services): Promise<void> {
    await (await accept(transport, services)).closed;
}

export async function connect(transport: Transport, services: ClientServices): Promise<Connection> { /* … */ }

// Also here, for the `comline@2` handshake: `negotiated` and `warnings`, which
// read what it agreed, and `@internal` `HELLO` and `handshake()`.
```

`wire.ts` holds what every file of the package shares:

```ts
/** The package's wire format (`wire.format`). */
export const Format: Codec = new PackedCodec();

/** Digest of every schema in the package — what a connection's handshake
*  checks, so both ends agree on each protocol's number. */
export const CONNECTION_IR_HASH = 0x1ad273c98d4e98fbn;
```

Each protocol's file has its interface, its sender, and the plumbing:

```ts
// conformance.ts
export interface ChatSendParams {
    n: number;
}

/** @internal */
export const ChatSendParamsLayout: Layout = { struct: [["n", "u32"]] };

export interface Chat {
    send(peer: Peer, params: ChatSendParams): Promise<number>;
}

/** @internal */
export const CHAT_CALLS = ["send"] as const;

/** @internal */
export class ChatDispatcher implements Dispatch {
    /** This protocol's number on a connection. */
    static readonly PROTOCOL = 0;
    constructor(impl: Chat) { /* … */ }
    provideOn(conn: Connection): void { /* … */ }
    // …
}

/** Calls protocol `Chat` on the other end of a connection: the peer a `Connection` reaches, or the one a handler was given. */
export class ChatSender {
    constructor(peer: Peer) { /* … */ }

    async send(params: ChatSendParams): Promise<number> {
        checkCall(this.peer, ChatSender.PROTOCOL, 0, "conformance::Chat", "send");
        const env = await this.peer.call(ChatSender.PROTOCOL, { id: 0, name: "send" }, params, { layout: ChatSendParamsLayout });
        // …
    }
}

// Events, EventsDispatcher (PROTOCOL = 1) and EventsSender, the same way;
// `ping` is one-way, so `EventsSender.ping()` resolves to `void`.
```

`u32` is a `number`; a `u64` would be a `bigint`. The plumbing is exported, so
you can wire a connection [by hand](#by-hand), and `@internal`, so it isn't what
you call: the `…ParamsLayout` constants, the `…_CALLS` tables, and the
dispatchers (`provideServices` builds them, so you don't name one). With
`datagram@2` and `comline@1`, the comment is the same, `accept` and `connect`
call `Connection.accept(transport, Format, CONNECTION_IR_HASH)` without a
handshake of their own, and there is no `checkCall`.

It differs from a client and server in three ways:

- **Handlers take the peer first:** the other end of the connection the call
  came in on. Through it a handler calls back (`new EventsSender(peer)`),
  reads `peer.id`, and keeps data on the connection in `peer.extensions`.
- **A sender replaces the client,** over anything that implements `Peer`: a
  `Connection`, or a handler's peer. A call with a deadline goes through
  `peer.call(…, { timeoutMs })` by hand: the generator doesn't read
  `@timeout_ms` yet.
- **`CONNECTION_IR_HASH`** covers every schema in the package. It also fixes
  each protocol's number (`ChatDispatcher.PROTOCOL`), its position among the
  package's protocols.

There's no `serveChat` helper: the package's `serve` serves them all. Protocols on
`datagram` in the same package keep their `Client` and server, and so do
`jsonrpc` ones unless the package has a JSON-RPC protocol on a connection (see
[Over JSON-RPC](#over-json-rpc)).

## By hand

The package's functions are a few lines over the runtime's `Connection`,
which is also how to pick another codec for one connection. For the default
`datagram@3` and `comline@2`, the package's `handshake()` is the handshake:

```ts
import { Connection, Datagram3Framing } from "@comline/runtime";
import { CONNECTION_IR_HASH, Format } from "./generated/wire.js";
import { handshake } from "./generated/connection.js";

// The side that accepts.
const agreed = handshake();
const server = await Connection.accept(transport, Format, CONNECTION_IR_HASH, new Datagram3Framing(), agreed);
server.extensions.set(agreed.negotiated!);
new ChatDispatcher(chatImpl).provideOn(server);

// The side that dials.
const client = await Connection.connect(transport, Format, CONNECTION_IR_HASH, new Datagram3Framing(), handshake());
new EventsDispatcher(eventsImpl).provideOn(client);
const sent = await new ChatSender(client).send({ n: 3 });

// The server calls the client on its own.
await new EventsSender(server).shown({ n: 7 });
```

The package's `accept` and `connect` keep what `comline@2` agreed in the
connection's extensions, as the `server.extensions.set(…)` line does, for
`negotiated` and `warnings` to read and for each sender to check before it
calls. A connection opened without it has nothing to check against, and every
call goes. On `datagram@2` and `comline@1` there's nothing to keep, and
`Connection.accept(transport, Format, CONNECTION_IR_HASH)` is all of it.

A connection starts reading as soon as it's made, and `closed` resolves when
the transport closes. Calls still waiting then reject with a `transport`
error. A request to a protocol this side doesn't provide is answered with a
fault.

## Over JSON-RPC

A JSON-RPC protocol the client provides runs on a connection too, and then so
do the package's other JSON-RPC protocols
([the rules](../../guides/idl/protocol.md#json-rpc-on-a-connection)). Pass
`JsonRpcConnectionFraming` to both ends (the package's `serve` and `connect`
do, with a `JsonCodec`); the rest of this page is unchanged:

```ts
import { Connection, JsonCodec, JsonRpcConnectionFraming } from "@comline/runtime";

const server = await Connection.accept(transport, new JsonCodec(), CONNECTION_IR_HASH, new JsonRpcConnectionFraming());
const client = await Connection.connect(transport, new JsonCodec(), CONNECTION_IR_HASH, new JsonRpcConnectionFraming());
```

- **Each call table holds method names:** `["send"]`, or under
  `method_names = qualified`, `["chat.Events/shown", "chat.Events/ping"]`.
  A request is routed to the provided protocol whose table has its method.
- **A one-way call is a notification,** sent with no `id`. A request without
  one gets no reply, even if its function returns a value.

A JSON-RPC protocol that stays off a connection keeps its client and server:
`serveRpc(impl, transport)` and `RpcClient.connect(transport)`, which encode
JSON over `JsonRpcFraming`.

## A handler calling back

```ts
class Sent {
  constructor(public count: number) {}
}

const chatImpl: Chat = {
  async send(peer, { n }) {
    await new EventsSender(peer).shown({ n });
    const sent = peer.extensions.get(Sent) ?? new Sent(0);
    sent.count++;
    peer.extensions.set(sent);
    return sent.count;
  },
};
```

`Extensions` holds one value per class. It belongs to the connection, so
`Sent` counts this client's messages and no one else's.

## Concurrency

- **Several calls can be in flight.** A reply goes to the call with its
  request id, so `Promise.all` over a sender's calls works. (On a lockstep
  `Client`, concurrent calls can take each other's replies.)
- **The peer's requests are handled one at a time, in order,** except while
  every running handler is waiting on a call to the peer. Then the next
  request starts, since it may be the nested call that handler needs.

## Without generated code

`conn.provide(protocol, dispatcher)` registers any `Dispatch`. One that
needs the peer implements the optional `dispatchWith(kind, params, reply,
peer)`. `Peer` has `codec`, `id`, `extensions`, `call(protocol, call, params,
{ timeoutMs })` and `notify`. `Datagram2Framing` is the default framing; another
`ConnectionFraming`, such as `JsonRpcConnectionFraming`, can be passed to
`connect`, `accept` or `Connection.unverified`.
