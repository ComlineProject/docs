# Dependency pins in generated code

Status: **under discussion** · Raised by
[comline-rust#144](https://github.com/ComlineProject/comline-rust/issues/144)
· Builds on the 1.0 publishing requirement in
[Offline supply](offline/supply.md) and [Readiness](../conduct/readiness.md)
([runtime#115](https://github.com/ComlineProject/runtime/issues/115),
[comline-typescript#154](https://github.com/ComlineProject/comline-typescript/issues/154))

**The question:** how a build that uses generated code ends up with exactly
one copy of each Comline runtime package: by construction, not by care, both
before 1.0 and from it.

Four parts, each removing one way it goes wrong:

1. **One Comline dependency per generated package.** It reaches everything
   else through that one dependency, so the generated package's own pins can't
   disagree.
2. **Versions instead of git revs, from 1.0.** The package manager merges
   compatible requirements, whoever wrote them.
3. **The emitted version comes from the build,** not from a constant someone
   edits by hand.
4. **Checks in CI** that fail on a second copy, on a lower bound that isn't
   true, and on an API break within a major version.

Parts 1 and 4 work with git revs, so they can land now. Parts 2 and 3 come
with publishing, which 1.0 already requires.

## The problem

A lib-mode Rust crate generated today pins two Comline crates, each by git rev:

```toml
comline-runtime = { git = "https://github.com/ComlineProject/runtime", rev = "e7362217e95f…" }
comline_std = { git = "https://github.com/ComlineProject/comline-rust", rev = "fa2b4cc65cbd…" }
```

`comline_std` at `fa2b4cc` depends on `comline-runtime` at `3b9cc9dc53a8`. Cargo
treats two revs as two packages, so the runtime is built twice. It works
today only because no `comline_std` type crosses into the generated API. The
day one does, the two copies' types won't match, and the generated code
won't compile.

### Where the pins come from

There are four places where a runtime version is written down, and nothing
ties them together:

| Pin | Written by | How it drifts |
|---|---|---|
| `RUNTIME_REV` | comline-rust's codegen, by hand | Bumped on its own. |
| `comline_std`'s own runtime pin, reached through `STD_REV` | comline-rust's `std-extra/Cargo.toml` | `STD_REV` must name a commit that already exists, so the commit that bumps `std-extra` can't name itself. Every runtime bump leaves `STD_REV` one step behind until someone follows up (comline-rust#144: #140 bumped `std-extra`, `STD_REV` stayed at `fa2b4cc`). |
| The user's own pin | The user | A user who needs a runtime item or feature, such as `transport::tokio::Tcp`, adds `comline-runtime` themselves and has to copy the generated rev by hand. A copy made a week earlier is a second runtime. |
| A second generated package | A different generator version | Two packages generated by different CLI versions pin different revs. |

### Why releasing carefully doesn't fix it

**Git revs never merge.** Two revs a single commit apart are as separate to
Cargo as two unrelated crates, so every pin above must be exactly equal, by
hand, across repos. The chicken-and-egg in the second row means even a
careful maintainer can't get it right in one commit.

### Why publishing alone doesn't fix it either

Publishing to crates.io and npm is already required for 1.0. It fixes the
merging: Cargo resolves `comline-runtime = "1.4"` and `"1.7"` to one copy.
But on its own:

- **Two Comline dependencies are still two edges to keep in step.** The
  generated crate's runtime requirement and `comline_std`'s can still name
  different majors.
- **A hand-written constant can still name the wrong version.** It just
  becomes a version string instead of a hash.
- **Before 1.0, `0.3` and `0.4` don't merge.** Cargo treats every `0.x` minor
  as incompatible, so publishing at `0.x` keeps today's problem.
- **Merging assumes compatibility.** Code generated against runtime 1.4 then
  builds against 1.9. That holds only if the runtime keeps its public API
  backward compatible within a major version, and nothing checks that today.

## Proposal

### 1. One Comline dependency per generated package

**Rust, `lib` mode** (`external_std` on): `comline_std` re-exports the
runtime (`pub use comline_runtime as runtime;`). The generated crate depends
only on `comline_std`, and reaches runtime items by full path through it
(`::comline_std::runtime::…`, in line with comline-rust#96's full paths).
`RUNTIME_REV` leaves the generated `Cargo.toml`.

**Rust, `code` mode** (`external_std` off): nothing changes. The generated code
already depends on the runtime alone.

**Users don't add their own pin.** The generated crate re-exports its one
dependency (`pub use comline_std;`) and forwards the runtime's optional
features:

```toml
# generated Cargo.toml
[features]
tokio = ["comline_std/tokio"]   # comline_std forwards to comline-runtime/tokio
```

A user writes `greeter = { …, features = ["tokio"] }` and uses
`greeter::comline_std::runtime::transport::tokio::Tcp`. There is no Comline pin
in their `Cargo.toml` to drift.

**TypeScript:** the same shape. `@comline/std` re-exports `@comline/runtime`,
and the generated package lists `@comline/std` as a `peerDependency`, so npm
installs one copy for the application, not one per generated package.

**Before 1.0, this alone fixes comline-rust#144.** The generated crate then
has one pin, `STD_REV`, and the runtime is whatever that `comline_std` pins.
`STD_REV` can still lag a runtime bump, but a lag can no longer make two
copies.

### 2. Versions instead of git revs, from 1.0

Generated code names a semver range:

```toml
comline_std = "1.4"
```

- **Cargo merges every `1.x` requirement into one copy:** the generated
  crate's, a second generated crate's from another CLI version, and a user's
  own if they add one anyway. A second copy is then only possible across
  majors, and that is deliberate, and visible as a type error.
- **What it asks of the runtime and std:** the public API stays backward
  compatible within a major version, so code generated against 1.4 builds
  against 1.9. Part 4 checks this.
- **Wire compatibility is a separate question.** It is covered by
  [Schema compatibility](schema-compatibility.md) and the handshake, not by
  package versions.

### 3. The emitted version comes from the build

comline-rust's codegen and `std-extra` live in one workspace, so:

- **`comline_std`'s runtime requirement** is declared once, in
  `[workspace.dependencies]`.
- **The version codegen emits for `comline_std`** is read from `std-extra`'s
  own manifest at build time, by `build.rs` setting `COMLINE_STD_VERSION`,
  instead of being a constant. Bumping `std-extra` bumps what codegen emits,
  in the same commit.
- **Codegen and `std-extra` release together,** under one tag and one version
  number.

This removes the chicken-and-egg: **a version number can be named before
its release exists; a git rev can't.** The commit that bumps `std-extra` to
`1.5.0` also makes codegen emit `"1.5"`, and both publish from that one tag.

The same holds for TypeScript: the generator reads `@comline/std`'s version
from its `package.json` in the same repo.

### 4. Checks

In comline-rust (and comline-typescript, for npm):

- [ ] **One copy:** generate the conformance packages in `lib` mode, then fail
  if `cargo metadata` lists more than one `comline-runtime` or `comline_std`
  (for npm, more than one `@comline/runtime` in `npm ls`). This catches any
  cause, not only today's, and works with git revs.
- [ ] **True lower bounds** (from 1.0): build the generated crates at the
  lowest versions their requirements allow (`cargo +nightly update -Z
  minimal-versions`). An emitted `"1.4"` then really means 1.4 works, not just
  whatever is newest.
- [ ] **No API break within a major** (from 1.0): `cargo-semver-checks` in the
  runtime's and comline-rust's CI, against the last published release; an API
  report diff for the TypeScript packages.
- [ ] **Release order, automated** (optional): publishing runs runtime →
  comline-rust (std and codegen) → cli. Each release opens the bump PR in the
  next repo, so no step depends on someone remembering it.

## Before 1.0

In order:

1. **comline-rust#144's immediate fix:** bump `STD_REV` to `86d5f21` or later.
2. **Part 1:** `comline_std` re-exports the runtime, generated lib crates depend
   on it alone, and the features are forwarded. `STD_REV` becomes the only
   emitted pin.
3. **Part 4's one-copy check,** in comline-rust and comline-typescript CI.

Parts 2 and 3, and part 4's other checks, come with publishing.

## Not covered

- **The toolchain's own pins** (`core`, `generation` and codegen inside the
  CLI) are the same kind of problem, but stay inside the toolchain's build
  instead of reaching a user's
  ([Generation](../design/generation.md) already asks for one `comline-core`
  per tree). The one-copy check from part 4 applies to the CLI's CI as well.
- **Wire compatibility between runtime versions:**
  [Schema compatibility](schema-compatibility.md) and the handshake.

## Open questions

1. **Which package is the one dependency?** `comline` on crates.io is the
   CLI's name, so it can't be a facade. The recommendation is `comline_std`,
   which `lib` mode already depends on. A new crate would add a third package
   to release for no gain.
2. **Lockstep versions for codegen and `std-extra`?** The recommendation is
   yes: one tag, one version. Two versions in one repo invite the same drift
   this proposal removes.
3. **`build.rs` reading the manifest, or codegen depending on `comline_std`**
   and reading a `VERSION` const? The const is simpler, but it puts the
   runtime into the CLI's build. `build.rs` keeps the CLI lean.
